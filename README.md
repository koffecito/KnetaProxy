Kneta разбирает конфигурации из ваших источников, проверяет их через Xray, отсеивает IP, заблокированные в РФ, формирует подписки и при желании отправляет сводную статистику в Telegram. Всё работает на GitHub Actions по расписанию.

> [!WARNING]
> **Kneta не предоставляет VPN-серверы и не гарантирует доступность или безопасность сторонних узлов.**
> - Проверка показывает только то, что сервер сейчас отвечает. Она не доказывает, что ему можно доверять.
> - Владелец стороннего сервера технически может видеть ваш трафик. Не вводите пароли и не передавайте важные данные через узлы, которым не доверяете.
> - Анонимность и защита данных не гарантируются.
> - Используйте только те источники и конфигурации, которые вы вправе использовать, и соблюдайте применимые законы и правила сервисов. Ответственность за выбор и применение лежит на вас.

## ⚡ Быстрый старт

1. **Источники.** Создайте секрет `SUBSCRIPTIONS` со ссылками на подписки (раздел 1).
2. **Кэш.** Создайте секрет `CACHE_SALT` с любой случайной строкой (раздел 4).
3. **Telegram** (по желанию). Создайте бота, добавьте токен в секрет и ID чата в файл (разделы 2, 3, 4).
4. **Запуск.** *Actions → Check proxies → Run workflow*.
5. **Результат.** В папке [`sub/`](sub/) появятся `working.txt` и `all.txt`.

Дальше проверка идёт сама: **04:00 и 16:00 UTC**.

## ✨ Возможности

- загружает источники подписок из GitHub Secret `SUBSCRIPTIONS`;
- поддерживает конфигурации `vless://`, `vmess://`, `trojan://`, `hysteria2://` и `hy2://`;
- разбирает конфигурации, удаляет дубликаты и проверяет соединения;
- использует Xray для проверки соединения и Cheburcheck для проверки IP;
- поддерживает дополнительный режим проверки `generate_204`, `tcp` или `no`;
- определяет внешний IP и страну, когда это возможно;
- формирует основную подписку максимум из 100 конфигураций и полную подписку из всех прошедших проверку;
- запоминает результаты проверок, чтобы повторные запуски шли быстрее;
- сохраняет отчёт и историю результатов;
- может отправлять сводку в Telegram;
- запускается по расписанию через GitHub Actions.

## 🔄 Как работает проект

```text
Источники → Разбор и дубликаты → Xray → Cheburcheck → Подписки → Telegram
```

1. Читает источники из секрета `SUBSCRIPTIONS`.
2. Загружает URL-источники и принимает поддерживаемые прямые конфигурации, если они указаны отдельными строками.
3. Разбирает конфигурации и удаляет дубликаты.
4. Если IP конфига уже известен из кэша как заблокированный, конфиг сразу отбрасывается без запуска Xray.
5. Остальные конфиги проверяет через Xray. IP только тех из них, что прошли проверку, один раз отправляет в Cheburcheck: так запросов к нему примерно вдвое меньше. Cheburcheck начинает работать, не дожидаясь конца Xray. IP с временными ошибками Cheburcheck (429, 5xx, таймаут) перепроверяются вторым проходом.
6. Формирует основную подписку `sub/working.txt` и полную `sub/all.txt`: сначала идут конфиги, которые дольше всего подряд были рабочими. Если рабочих конфигов нет (например, недоступны все источники), прошлые подписки не перезаписываются.
7. Записывает статистику в `sub/report.txt`, историю в `sub/history.json` и краткую сводку с временем обновления в `sub/stats.json` (её читает сайт).
8. Если настроены Telegram-токен и ID чатов, отправляет сводное сообщение.

## 📋 1. Настройка источников подписок

Источники хранятся в GitHub Secret `SUBSCRIPTIONS`.

1. Откройте репозиторий проекта на GitHub.
2. Перейдите в **Settings → Secrets and variables → Actions**.
3. Нажмите **New repository secret**.
4. В поле **Name** укажите точно `SUBSCRIPTIONS`.
5. В поле **Secret** вставьте URL источников, каждый на отдельной строке. Поддерживаемые прямые конфигурации также можно указывать отдельными строками.
6. Нажмите **Add secret**.

Пример формата (адреса демонстрационные, они не являются рабочими источниками):

```text
https://example.com/subscription-one
https://example.com/subscription-two
```

> [!CAUTION]
> Не вставляйте реальные ссылки и конфигурации в README, issues, сообщения коммитов или обычные файлы репозитория.

## 🤖 2. Создание Telegram-бота

Telegram-бот нужен только для отправки отчётов. Если уведомления не нужны, настройку Telegram можно пропустить: проверки продолжат работать, но сообщение отправлено не будет.

### Шаг 1. Создайте бота через BotFather

1. Откройте Telegram и найдите официальный аккаунт **@BotFather**.
2. Нажмите **Start** или отправьте `/start`.
3. Отправьте команду `/newbot`.
4. Укажите отображаемое имя, например `MyProxy Reports`.
5. Придумайте уникальный username, который заканчивается на `bot`, например `myproxy_reports_bot`.
6. BotFather выдаст API-токен. Скопируйте его и храните в безопасном месте.

> [!CAUTION]
> **Токен — это секретный ключ управления ботом.** Не публикуйте его, не добавляйте в код и не отправляйте в чаты. Если токен стал известен другим людям, отзовите или перевыпустите его через BotFather и обновите секрет в GitHub.

### Шаг 2. Откройте чат с ботом

- **Личный чат:** откройте бота по username и нажмите **Start**. Бот не может первым начать личную переписку.
- **Группа:** добавьте бота в группу, куда должны приходить отчёты. Убедитесь, что он может отправлять сообщения.
- **Канал:** добавьте бота в канал и выдайте необходимые права на публикацию.

После этого получите ID нужного чата по инструкции ниже.

## 🆔 3. Получение ID чата

В `telegram/telegram_chats.txt` указываются **числовые ID чатов**, а не username и не токен бота. Каждый ID должен быть на отдельной строке. Можно указать несколько чатов: отчёт будет отправляться в каждый из них.

### Вариант A. Через Telegram Bot API

1. Откройте личный чат со своим ботом и нажмите **Start**. Для группы добавьте бота и отправьте сообщение в группе.
2. Откройте в браузере адрес `https://api.telegram.org/bot<TOKEN>/getUpdates`, заменив `<TOKEN>` токеном, который выдал BotFather.
3. В JSON-ответе найдите объект `message`, а внутри него объект `chat` и поле `id`. Это ID чата.
4. Скопируйте только числовое значение `id` в `telegram/telegram_chats.txt`.
5. Не публикуйте URL из адресной строки: в нём находится токен бота.

Если ответ пустой, отправьте боту новое сообщение и повторите запрос. `getUpdates` может не показывать обновления, если они уже были получены другим способом или у бота настроен webhook. Для группы ID часто отрицательный и может начинаться с `-100`.

### Вариант B. Через бота, который показывает ID

Можно воспользоваться известным Telegram-ботом для просмотра user/chat ID. Следуйте его подсказкам и проверьте, что получили ID именно нужного личного чата, группы или канала. Такие сторонние боты не связаны с Kneta: не передавайте им токен своего бота и не отправляйте конфиденциальные данные.

### Добавьте ID в `telegram/telegram_chats.txt`

Формат файла:

```text
123456789
-1001234567890
```

Это демонстрационные значения, замените их своими ID. Не добавляйте в файл токен бота. В текущей версии проекта ID читаются из `telegram/telegram_chats.txt`; одного создания секрета с ID недостаточно.

## 🔐 4. Настройка GitHub Secrets

В репозитории откройте **Settings → Secrets and variables → Actions** и создайте следующие секреты:

| Имя секрета | Обязателен | Что указать |
|---|---|---|
| `SUBSCRIPTIONS` | Да | URL источников и/или поддерживаемые прямые конфигурации, по одной строке |
| `CACHE_SALT` | Рекомендуется | Любая случайная строка, например `k8Xp2mQ7vR4tZ9nB`. Подробности в разделе «Кэш и секрет CACHE_SALT» |
| `TELEGRAM_BOT_TOKEN` | Только для Telegram | API-токен, выданный BotFather |

Чтобы добавить любой секрет:

1. Откройте **Settings → Secrets and variables → Actions**.
2. Нажмите **New repository secret**.
3. В поле **Name** введите имя секрета (например, `TELEGRAM_BOT_TOKEN`).
4. В поле **Secret** вставьте значение.
5. Нажмите **Add secret**.

GitHub Actions передаёт токен шагу Telegram-уведомления через переменную окружения. Если токен не задан, уведомление пропускается. ID чатов при этом берутся из `telegram/telegram_chats.txt`.

> [!NOTE]
> GitHub Secrets скрывает значение в настройках и позволяет workflow использовать его без записи в обычный файл проекта. Но он не защищает от кода, который намеренно выводит значение в логи. Не добавляйте команды, печатающие `TELEGRAM_BOT_TOKEN`, и не публикуйте URL, содержащие токен.

## 🧠 Кэш и секрет CACHE_SALT

Чтобы не проверять одни и те же IP в Cheburcheck при каждом запуске, Kneta запоминает ответы. Они хранятся в `sub/history.json` не в открытом виде, а как хэши, поэтому IP в публичном репозитории не видны.

Хэш считается от IP и секретной строки. Пока строка одна и та же, скрипт находит свои старые записи. Если строка поменялась, все записи становятся «чужими», и кэш как будто пустой.

> [!IMPORTANT]
> Раньше такой строкой был секрет `SUBSCRIPTIONS`, поэтому после каждой смены источников кэш терялся, и запуск становился в разы дольше. Теперь для этого есть отдельный секрет `CACHE_SALT`. Задайте его **один раз** и больше не меняйте и не удаляйте. Если его не создавать, всё продолжит работать, но с прежним недостатком.

Что даёт кэш:

- повторные запуски почти не обращаются к Cheburcheck;
- конфиги с IP, который уже известен как заблокированный, отсеиваются до запуска Xray;
- срок жизни записи случайный (25–100% от `CHEBURCHECK_CACHE_HOURS`), чтобы перепроверки равномерно распределялись по запускам.

## ⚙️ Режим дополнительной проверки

В `other/type.txt` укажите ровно один режим:

```text
generate_204
```

Доступные варианты:

- `generate_204`: дополнительная HTTP-проверка (по умолчанию `gstatic.com` и `cp.cloudflare.com`; достаточно, чтобы ответил любой; список задаётся переменной `GENERATE_204_URLS`). Рекомендуется;
- `tcp`: дополнительная TCP-проверка;
- `no`: дополнительная проверка отключена.

### Список URL для `generate_204`

`generate_204` — это адрес, который отвечает пустым ответом `204`. Проверка отправляет запрос через поднятый Xray-прокси: `204` значит, что трафик через конфиг проходит. Ответ `429` тоже считается успехом (сервис ответил через туннель, просто ограничил частоту), любой другой код или таймаут — нет. Проверка пройдена, если ответил **любой** из адресов.

Свой список можно задать переменной `GENERATE_204_URLS` (через запятую), например в workflow:

```yaml
      - name: Run checker
        env:
          SUBSCRIPTIONS: ${{ secrets.SUBSCRIPTIONS }}
          CACHE_SALT: ${{ secrets.CACHE_SALT }}
          GENERATE_204_URLS: "https://www.gstatic.com/generate_204,https://cp.cloudflare.com/generate_204"
        run: python checker.py
```

Советы: берите `https://`-адреса (они проверяют и TLS через туннель), смешивайте разных провайдеров, держите список коротким: для мёртвого конфига время проверки равно числу адресов × `REQUEST_TIMEOUT`.

Перед запуском Xray для конфигов на TCP-транспорте дополнительно делается быстрая проверка порта. Если порт не отвечает, конфиг отбрасывается сразу, не тратя время на Xray. Результат проверки `ip:порт` запоминается на время запуска.

## 🚦 Ограничения частоты (429)

- **Cheburcheck:** интервал между запросами автоматически растёт после ответа `429` (до `CHEBURCHECK_MAX_INTERVAL`) и возвращается обратно, когда ошибки прекращаются. Запросы идут с небольшим случайным разбросом, чтобы потоки не бились в лимит одновременно. `Retry-After` учитывается. IP с временными ошибками перепроверяются вторым проходом, а не отбрасываются.
- **Кэш:** вердикт по IP запоминается на `CHEBURCHECK_CACHE_HOURS` часов (по умолчанию 48; `0` отключает кэш).
- **Страна:** страна внешнего IP запоминается на `COUNTRY_CACHE_DAYS` дней.
- **Внешний IP** определяется через `EXIT_IP_API_URLS` (по умолчанию ipify, icanhazip, затем api.country.is): если сервис ответил `429` или не ответил, берётся следующий.
- **Неизвестная страна:** в режиме `generate_204` конфиг, который прошёл проверку доступности, но чей внешний IP или страну определить не удалось, не отбрасывается. Он попадает в полную подписку со страной «Неизвестно» (🏳️) и не занимает места в основной. В режимах `tcp` и `no` такие конфиги по-прежнему отбрасываются.
- **Отчёт:** в `report.txt` строка «Cheburcheck запросов» показывает, сколько ответов `429` пришло и сколько IP взято из кэша, а отдельная строка показывает, сколько конфигов отсеяно по кэшу до Xray.

## 🎛 Тонкая настройка

Все параметры необязательны. Их можно задать в блоке `env` шага **Run checker** в `.github/workflows/check-proxies.yml`.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MAX_WORKERS` | 32 | Сколько конфигов проверяется через Xray одновременно |
| `MAX_PROXIES` | 100 | Размер основной подписки |
| `REQUEST_TIMEOUT` | 5 | Таймаут запроса `generate_204`, секунды |
| `XRAY_READY_TIMEOUT` | 5 | Сколько ждать запуска Xray, секунды |
| `TCP_PRECHECK_TIMEOUT` | 3 | Таймаут быстрой проверки порта, `0` отключает её |
| `CHEBURCHECK_WORKERS` | 4 | Потоков запросов к Cheburcheck |
| `CHEBURCHECK_MIN_INTERVAL` | 0.8 | Начальный интервал между запросами, секунды |
| `CHEBURCHECK_MAX_INTERVAL` | 10 | Максимальный интервал после ответов 429, секунды |
| `CHEBURCHECK_CACHE_HOURS` | 48 | Срок хранения вердикта по IP, часы |
| `COUNTRY_CACHE_DAYS` | 14 | Срок хранения страны по IP, дни |
| `HISTORY_KEEP_RUNS` | 30 | Сколько запусков хранить записи о конфиге, который не встречается |

Оформление подписок (названия, интервал обновления, ссылка поддержки, анонс, суффикс в имени конфигов) задаётся в `other/info.txt`.

> [!TIP]
> Если запуск идёт слишком долго, сначала посмотрите в `report.txt` строку «Cheburcheck запросов»: если запросов много и почти нет «из кэша», дело в кэше (см. раздел про `CACHE_SALT`). Увеличивать `MAX_WORKERS` имеет смысл только после этого.

## ▶️ Запуск и расписание

Workflow расположен по пути `.github/workflows/check-proxies.yml`.

- **Автоматический запуск:** 04:00 и 16:00 UTC.
- **Ручной запуск:** откройте **Actions**, выберите workflow **Check proxies** и нажмите **Run workflow**. В поле `xray_version` можно указать другую версию Xray-core (например `v26.10.21`). Если оставить пустым, берётся версия, зафиксированная в `check-proxies.yml` (переменная `XRAY_VERSION`). Бинарник кэшируется по версии, поэтому при её смене скачивается заново.
- **Лимит времени:** запуск прерывается, если идёт дольше 40 минут.

Workflow устанавливает Python и Xray, проверяет настройки, запускает `checker.py`, сохраняет обновлённые результаты в репозитории, а затем отправляет Telegram-отчёт при наличии токена (сбой Telegram не отменяет сохранение). Одновременно выполняется только один запуск.

После настройки выполните первый запуск вручную и проверьте шаги **Validate project**, **Run checker** и **Send Telegram stats** в журнале GitHub Actions.

> [!NOTE]
> Первый запуск на пустом кэше (или после смены `CACHE_SALT`) идёт заметно дольше обычного: все IP проверяются в Cheburcheck заново. Со следующих запусков время сокращается.

| [`all.txt`](sub/all.txt) | Полная подписка из конфигураций, прошедших проверки |
| [`report.txt`](sub/report.txt) | Итоги запуска, статистика и ошибки |
| `history.json` | Сколько запусков подряд каждый конфиг был рабочим и кэш проверок (хэш-ключи; давно не встречавшиеся записи удаляются) |
| `stats.json` | Время последнего обновления, число конфигов, стран и протоколов (используется сайтом и подходит для бейджей) |

Статистика по странам и протоколам в Telegram относится к **основной подписке `working.txt`**, а не ко всему набору найденных конфигураций. Результаты отражают состояние на момент проверки и не гарантируют дальнейшую доступность узлов.

## 💻 Локальный запуск

Нужны Python 3.11+, зависимости из `other/requirements.txt` и установленный Xray.

```bash
pip install -r other/requirements.txt
xray version
```

Перед запуском задайте переменную окружения `SUBSCRIPTIONS` с многострочным содержимым, а при желании ещё `CACHE_SALT`. Не записывайте реальные источники в файл, который попадёт в Git, и не передавайте секрет прямо в командной строке, если она может сохраняться в истории оболочки.

Затем выполните:

```bash
python other/validate.py
python checker.py
python telegram/telegram_notify.py
```

Для локальной отправки отчёта также задайте `TELEGRAM_BOT_TOKEN` и заполните `telegram/telegram_chats.txt`. Если токен не задан или список ID пуст, отправка будет пропущена.

## 🛠 Устранение неполадок

| Проблема | Что делать |
|---|---|
| `SUBSCRIPTIONS` отсутствует | Проверьте точное имя секрета и что он создан в настройках нужного репозитория |
| Workflow не видит секрет | Секреты могут быть недоступны некоторым запускам из форков; проверьте источник запуска |
| Запуск стал долгим | Проверьте, не менялся ли `CACHE_SALT`, и посмотрите строку «Cheburcheck запросов» в `report.txt` |
| Много ответов 429 | Это нормально на пустом кэше. Со следующих запусков запросов станет меньше |
| Сообщение Telegram не приходит | Проверьте токен, нажмите **Start** в личном чате или добавьте бота в группу/канал, затем перепроверьте ID |
| `chat not found` | Указан неправильный ID либо бот не имеет доступа к чату |
| `bot was blocked by the user` | Откройте личный чат с ботом и нажмите **Start** |
| В статистике нет стран или протоколов | Проверьте `sub/report.txt` и соответствие заголовков ожидаемому формату |
| Конфигурация отсутствует в результате | Она могла иметь неверный формат, дублироваться или не пройти одну из проверок |
| Запуск прерван по времени | Уменьшите число источников или увеличьте `timeout-minutes` в workflow |

## ❓ Частые вопросы

**Можно ли менять `SUBSCRIPTIONS` когда угодно?**
Да. Если задан `CACHE_SALT`, кэш при этом сохраняется.

**Что будет, если поменять `CACHE_SALT`?**
Кэш перестанет находиться, и следующий запуск будет долгим, как первый. Данные не ломаются, просто всё проверится заново.

**Почему в основной подписке меньше конфигов, чем в полной?**
В основную попадают до 100 лучших конфигов с известной страной, отсортированных по числу запусков подряд, в которых они были рабочими. В полную попадают все прошедшие проверку.

**Нужен ли Telegram?**
Нет. Без него проект работает так же, просто сводка не отправляется.

**Гарантирует ли проверка, что конфиг будет работать у меня?**
Нет. Она показывает состояние на момент запуска с серверов GitHub. Ваш провайдер и регион могут вести себя иначе.
